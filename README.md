# Codex × DeepSeek Harness：分层协同架构

> 状态：设计草案，尚未实现。目标：在研究与开发中减少重复审查和不必要的强模型调用，同时保留对关键结果的有效检查。

## 1. 问题与目标

本项目探索让 Codex 与 DeepSeek Harness（DSH）协同：利用 DSH 执行适合委派的任务，让 Codex 处理任务规划、必要审查和复杂问题，依据任务实际影响选择验证深度。目标是缩短从需求到可用结果的时间，并让调用成本与工作价值相称。

适用任务包括代码修改、MATLAB 仿真脚本、数据处理和研究文档。系统应记录足够的证据，帮助用户判断结果，同时避免默认生成多份任务卡、重复执行冒烟或消融测试，以及过早建立兼容层与回退方案。

**非目标**：首版不构建完整多智能体平台，不承诺自动选择最优模型、不自动发布或合并、不假设不同产品订阅或账户之间可直接共享额度。图示中的 Astra、Sol-Lite、Sol-Full 在本项目中只是职责/审查级别，具体可用模型及权限须以实际环境为准。

## 2. 已知事实与待验证内容

- DSH 是 DeepSeek 开源的 agent harness，采用插件架构；官方仓库标注其处于开发者预览阶段，接口可能变化。[DSH 官方仓库](https://github.com/deepseek-ai/deepseek-harness)
- DSH 有官方桌面端；桌面端的存在不等于其对外暴露稳定、受支持的任务调度接口。[桌面端说明](https://github.com/deepseek-ai/deepseek-harness/tree/master/apps/desktop)
- Codex 与 DSH 能否由外部进程以用户现有账户、授权方式进行程序化调用，必须分别检查实际版本、官方文档和本机设置。不可假定桌面订阅可转为 API 凭据，或假定存在特定 CLI/API。
- 路由效果、成本和速度均为待测目标，不能仅凭架构图宣称已经降低。

## 3. 推荐路线：先人工交接，再接入自动化

### 第一阶段：人工协同基线

1. 用户指定任务和工作目录，明确期望结果及必要约束。
2. Codex 判断是否适合交给 DSH，并生成简短任务说明；可在 DSH 中由用户手动提交。
3. DSH 在约定工作区实施，运行与改动相称的检查，报告结果。
4. Codex 根据实际影响和变更证据复核，低风险任务不强制再次审查；复杂问题才升级。
5. 记录完成时间、可取得的调用成本或用量、验证结果及返工次数，作为后续比较基线。

这个阶段可以先检验协作方式是否有价值，不依赖未知接口。避免多个 agent 同时修改同一工作目录；交接时固定任务范围，并用 Git 差异或明确文件清单确认交付内容。

### 第二阶段：验证真实集成能力

在确定 DSH 版本后，查阅官方文档和源码，验证是否存在受支持的无交互任务入口、插件扩展、任务状态及结果获取方式；分别验证 Codex 可用入口、授权、费用及限制。做一次最小端到端调用验证，再决定使用何种适配器。桌面操作本身不能证明存在稳定自动化接口。

### 第三阶段：最小自动路由

仅在两端接口可用后增加协调器：读取任务，调用 DSH 适配器，接收结果，根据任务影响和验证结果选择完成、轻量审查、深入分析或请求用户决定。每一步要能显示当前状态、失败原因和下一步，允许用户接管。

## 4. 建议组件

```text
用户任务
   ↓
任务说明与范围确认
   ↓
协调器（可先由人工执行）
   ├─ DSH 适配器：执行任务、返回变更与结果
   ├─ 验证器：运行本次必要检查
   └─ 路由器：结合影响和结果决定是否审查或升级
                     ↓
              Codex 审查 / 用户决定
```

- **任务说明**：目标、工作目录、范围、验收条件、需要保留的约束。按需填写，不强制大量模板。
- **DSH 适配器**：负责将任务提交给经验证的 DSH 接口、观察状态、收集输出；首版可以是人工交接。接口尚待验证，不能预设实现细节。
- **验证器**：优先复用项目现有命令，只运行能够回答当前问题的检查；不将“未运行”标记为“通过”。
- **路由器**：依据实际影响、检查结果和失败情况作决定，而非单纯看文件数量。保留人工覆盖。
- **审查者**：在必要时读取任务说明、关键差异、验证证据及相关原始代码/数据，不能仅凭执行方摘要断言正确。

## 5. 路由规则

| 情况 | 默认处理 |
| --- | --- |
| 文案、图表排版、局部可逆修改；不影响研究计算 | 执行并做一次相称的基本验证；无需强模型例行复审 |
| 修改计算公式、样本选择、归一化、随机种子、评价指标、实验配置 | 检查受影响的核心行为和结果；判断是否需要重跑相关实验，必要时审查 |
| 安全权限、数据完整性、公共接口、关键研究结论或方向发生变化 | 提升审查力度，由 Codex 分析，必要时由用户决定 |
| 检查失败、信息不足或反复修复无进展 | 保留证据并升级分析；不把失败或未验证结果包装为通过 |

这些是可调整的启发式规则，不是经过验证的量化评分。文件改动很少也可能影响实验结论。没有新改动、失败或未解决疑点时，不重复执行相同验证；消融实验仅在方法评估问题需要时安排。

## 6. 任务与结果的最小协议（草案）

任务和结果可以从普通 Markdown 开始，待自动化确有需要时再固化为机器可读格式。字段如下：

**任务**：ID、目标、工作区及基线版本、修改范围、验收条件、必要限制。

**结果**：任务 ID、执行状态、修改文件和关键差异、运行过的检查及结果、未运行的检查与原因、影响判断、需要决策的问题。

执行状态至少区分 `completed`、`needs_review`、`blocked`、`failed`；检查状态区分 `passed`、`failed`、`not_run`。以上是设计建议，不表示 DSH 已提供这些字段。

## 7. 最小可行版本与验收

**MVP**：选择一个真实但范围小的项目任务，完成一次 Codex → DSH → 必要验证 → 结果交接。初次允许人工交接，暂不要求自动调度。

**验收标准**：

1. 能说明各方职责、工作目录和交接时使用的任务及结果。
2. DSH 交付的变更可定位，检查结果可复核，未运行项目明确标注。
3. 路由决策能说明具体原因；低风险任务无需强模型例行最终验收。
4. 记录总耗时、可获得的调用成本或用量、返工次数，与单独使用 Codex 的同类任务作可比观察；暂时不能精确归因时明确记录。
5. 高影响研究改动能追溯关键计算和数据依据；不以测试通过替代科研判断。

## 8. 需解决的问题

- 当前安装的 DSH 桌面版本、可调用入口和支持的自动化能力是什么？
- Codex 与 DSH 在本机分别采用什么授权方式？程序调用和桌面交互是否具有相同权限与计费方式？
- 哪个实际课题适合作为首个试点，且可以明确提供基线、验收与比较方法？
- 自动化运行时如何隔离并归属工作区写入，以避免两个 agent 并发覆盖？
