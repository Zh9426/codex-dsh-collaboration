# Codex 与 DeepSeek Harness 协作：设计草案

## 使用场景和目标

用户在 Codex 中打开或新建项目并提出目标。部署一次后，协作能力默认可在后续项目中使用；用户可以针对某次任务要求不使用。Codex 结合任务和项目约束，自行决定直接处理、委派 DeepSeek Harness，或请其他 Codex 模型分析。用户无需手工在模型之间搬运上下文。

## 职责分工

- **Terra 主协调**：与用户沟通，理解目标、判断影响、选择处理方式、组织交接并汇报结果。
- **DeepSeek Harness 执行**：在指定项目和任务范围内直接修改文件、自检并汇报结果。
- **Sol 深入分析与审查**：按需分析复杂代码、跨模块问题、关键计算变更及主协调者无法判断的问题，查看必要的原始证据。
- **Astra 重大决策**：按需分析重大架构取舍、研究可信度及复杂疑难问题；需要用户决策时呈现依据。
- **Luna 轻量整理**：只有长日志提取、资料整理等任务单独调用确有价值时才使用。

模型和角色的映射是可调整的初始方案。主会话保持协调；其他 Codex 模型由已配置的对应子代理承担，不假定主会话能自动切换自身模型。

## 默认路由触发条件

1. Terra 先判断目标和实际影响。若架构、数据口径或研究方法有会实质改变结果的未决选择，先请 Astra 分析，再决定实施边界；需要用户决定时呈现依据。
2. 范围明确且适合交接的实现优先给 DeepSeek；零碎任务可由 Terra 直接完成。DeepSeek 在工作区修改并自检。
3. 执行后依据改动影响做必要检查。关键计算、数据含义、权限、公共接口或主要结论受到影响，或检查失败、证据冲突、同一问题反复修复无进展时，请 Sol 针对性分析；若涉及方向性选择，再升级 Astra。
4. Luna 只在长材料单独整理确实节省主会话上下文时使用。这些条件可以组合，不是互斥的 `if/else` 链；也不因文件数量、固定分数或任务完成而自动多轮审查。

## 互联边界

Codex 是协作主导者，由它发起任务并协调后续步骤；DeepSeek Harness 是配合执行的工作端。DeepSeek 在受委派任务中返回结果、状态或问题，Codex 可以继续提出要求或回答。当前不需要 DeepSeek 自行启动 Codex 任务或主动唤醒 Codex 会话。

发送任务和返回结果可由一套支持交互的通信机制承担，不预设每个方向都要独立桥接。候选的 dsh-baton 通过 MCP 提供发送、等待、提问应答和后续指令，但在本机的兼容性和可靠性尚未验证。

## 流程原则

1. 先理解目标与约束。简单任务可以由主协调直接完成；适合委派的具体工作交给 DeepSeek。每个任务不必经过所有角色。
2. 交接只包含必要的目标、范围、背景和完成条件。DeepSeek 返回改动、实际验证结果和未解决问题。
3. 验证与实际影响相称。涉及数据筛选、标签、公式、评价指标、实验配置或主要结论时，要判断对结果和可信度的影响；必要时核对原始数据、代码和结果。
4. 测试通过并不自动证明科研结论可靠；文件少也不自动表示风险低。不用固定风险分数代替判断。
5. 出现反复失败、证据不足或重大分歧时，分析原因、调整处理方式并按需升级；不机械设定固定轮数。
6. 结果应说明做了什么、关键验证结果和影响判断的未解决问题；不强制日常任务生成任务卡、完整复盘或多轮审查。
7. 遵守项目既有要求及运行时权限；不默认绕过审批，不自动提交或推送，除非用户另有授权。

## 可选实现方式

1. **Codex 原生配置与现有 MCP 桥（优先评估）**：个人级 Codex 配置及相应角色说明支持跨项目复用；先评估社区项目 [dsh-baton](https://github.com/JialaoLiu/dsh-baton)，由 Codex 经 MCP 委派本机 Harness。Windows 和本机版本的实际兼容性、项目路径、权限及配置影响尚待验证。必要时再考虑自行编写少量适配代码。
2. **独立协调器**：一个单独程序调用 Codex 与 DeepSeek 并管理流程。自动化控制更集中，但引入额外状态和维护成本，也偏离用户在 Codex 主对话中工作的习惯。
3. **手工交接**：通过桌面界面复制任务和结果。接入成本低，但无法满足期望的自动协作体验。

## 实施和验证的关键问题

- 本机已发现 Harness 的 headless 命令和版本 0.2.2-rc.1；无论使用社区桥或 headless，它能否沿用桌面登录、在 Codex 运行环境中使用现有凭据以及按预期访问和修改指定项目，尚待实际验证。
- 个人级配置、主模型选择和自定义代理在用户所用 Codex 桌面环境中的实际生效方式及账户模型权限需要验证；上级运行规则、项目约束、沙箱和审批可能限制自动委派或文件访问。
- 应测试一次真实、范围受控的端到端任务：从 Codex 协调到 DeepSeek 修改、自检、结果回传与相称核查。单纯模拟调用或打印帮助信息不能证明整条链路可用。
- 凭据由既有工具管理；适配层不保存或输出密钥。不能将 API 价格直接等同于用户的 Codex 订阅消耗。

## 权限验证补充

- 用户确认此前的成功执行依赖人工批准，并将 Harness 会话切换为完全权限。故追加了独立测试，不把此前结果误判为工作区内修改免审批。
- 使用 Harness 自带 `headless`，显式选择 `workspace-write` 和当前默认权限各做一次隔离目录写入，均无需提升权限即可通过文件工具将 `marker.txt` 改为 `after` 加 LF；已独立核对字节并清理测试文件。默认权限已是 `workspace-write`，无需把它改成完全权限。
- 默认权限测试中，Harness 运行 PowerShell 进行字节核对时报告 `SetNamedSecurityInfoW failed (Win32 5): grantWrite(...)`，命令未启动。此错误与 Windows ACL 沙箱初始化有关；文件工具仍可写入。不能把「允许工作区写入」等同于「受限 shell 可在本机可靠执行」。
- dsh-baton 可把任务中的提问或审批等待状态返回 Codex，但当前未找到由 Codex 轻量模型代替用户批准 Harness 权限升级的现成工具。若要实现，需要单独设计批准范围、权限边界及桥接协议；不能以自动批准完全权限替代工作区写入。

## Windows ACL 故障处理

- 在 F: 盘的当前项目根目录，当前账户原先只继承 `Authenticated Users: Modify`，缺少显式的完全控制权限。Harness 对 `workspace-write` 会话根目录设置受限 shell 的临时写入授权时，报 `SetNamedSecurityInfoW failed (Win32 5): grantWrite(...)`。
- 已用 `icacls` 只给 `F:\project\codex-dsh-collaboration` 根目录增加 `ZH89\Zh89:(F)`，未递归修改子目录。变更前 ACL 保存在项目根目录的 `acl-before-dsh-test.txt`，并由 `.gitignore` 排除。
- 修复后，Harness 在该根目录以 `workspace-write` 运行受限 PowerShell，输出 `WORKSPACE_SHELL_OK`，未申请完全权限。以未修改权限的 `verification/permission-smoke` 子目录作为独立会话根目录时仍重现 Win32 5，验证该问题依赖会话工作区根目录的权限。
- 这次修复仅覆盖当前项目根目录。将来在 F: 盘新建的项目若继承相同权限，可能需要对那个项目根目录做同样的单目录修复；不应把整个 F: 盘改成完全控制。
- Harness 成功启动后还在目录上写入它自己的受限执行权限项。若要恢复本次试验前的完整目录 ACL，应在确认该项目无需继续运行 Harness 受限 shell 后，使用保存的 `acl-before-dsh-test.txt` 通过 `icacls` 恢复，而不只删除当前账户的授权条目；恢复时需先核对路径和备份内容。
